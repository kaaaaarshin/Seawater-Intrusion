1. RESEARCH BASIS AND SCOPE
Primary source:
Jiazhi Sun et al., “A novel analytical solution for quantifying seawater intrusion in coastal aquifers embedded with a cutoff wall,” Advances in Water Resources 212 (2026), article 105301, DOI: 10.1016/j.advwatres.2026.105301.

Use the supplied paper PDF as the scientific source of truth. If it is available in the project folder, inspect it before coding. If it is not available, ask the user where the PDF is rather than reconstructing the full model from memory.

The project follows the CONFined aquifer branch only. The inland boundary condition is CONSTANT INLAND FRESHWATER FLUX q_f. Use the sharp-interface analytical model described in the paper, not an LLM-based approximation and not a generic machine-learning model.

In scope:
- Confined coastal aquifer only.
- Steady-state analytical model from the paper.
- Constant inland freshwater flux boundary condition.
- Cutoff wall with published conductivity, thickness, location and opening-height parameters.
- Classification into the paper's applicable wall/interface scenarios.
- Analytical calculation of interface toe location x_t and hydraulic head profile phi(x).
- Interface elevation profile zeta(x), where supported by the confined-aquifer equations and the user's highlighted algorithm.
- Dimensional outputs in physical units.
- A generated CSV simulation dataset.
- Interactive frontend for configuration, running simulations, reviewing outputs, and visualizing profiles.
- Unit tests and validation against reference values/results explicitly reported in the paper.
- Clear display of model assumptions, parameter values, scenario labels, and validation status.

Out of scope unless the user later asks:
- Unconfined aquifer branch.
- Constant inland head boundary condition.
- SEAWAT or other numerical groundwater solver.
- Machine learning predictions.
- Adding mixing/dispersion corrections that are not required by the highlighted algorithm.
- Claiming that a generated simulation dataset is measured field data.

2. SCIENTIFIC MODEL RULES
Read the PDF carefully and implement the equations for the confined case, including the appropriate piecewise hydraulic-head equations, toe-location equations, and scenario conditions. The paper's main text and appendices must be consulted. In particular, inspect:
- Mathematical model and boundary conditions (Section 2).
- Confined-aquifer analytical solutions and scenario conditions (the equations around Eqs. 9–23 in the paper).
- Appendix A for dimensional solutions/derivations.
- Table 2 for physical parameter values.
- Results figures/tables and any reported numerical values used for validation.

Important definitions from the paper:
- Freshwater density rho_f = 1000 kg/m^3.
- Seawater density rho_s = 1025 kg/m^3.
- Density ratio alpha = rho_f / (rho_s - rho_f) = 40.
- Confined-aquifer freshwater flow-path thickness relation:
  h_i = alpha * phi_i - (alpha + 1) * H_s + H.
- Confined-aquifer interface elevation relation:
  zeta(x) = (alpha + 1) * H_s - alpha * phi(x).
Check the exact definitions, datum, and dimensional/dimensionless transformations in the paper before implementing. Do not silently substitute an equation from the unconfined branch.
- The coast boundary condition must follow the paper's confined-aquifer equation.
- The inland boundary condition is constant flux:
  K_a * h_i * (d phi_i / dx) at x=L equals q_f, using the paper's exact sign convention.
- Use the paper's dimensional recovery equations; do not assume dimensionless x values are metres.
- Wall-region flow may require piecewise equations because the wall conductivity differs from aquifer conductivity.
- Scenario classification must use the conditions stated in the paper, not guessed thresholds.

Do not implement the complete model by fitting curves to one published plot. Use the equations and boundary/continuity conditions. If any equation is ambiguous or illegible, report the ambiguity in a code comment and ask the user before making a scientific assumption.

Start with the values below from the paper's parameter table. Verify them against Table 2 in the supplied PDF before treating them as final.

Parameter | Symbol | Initial value | Unit

Aquifer hydraulic conductivity | K_a | 10 | m/day
Cutoff-wall hydraulic conductivity | K_w | 0.001 | m/day
Cutoff-wall thickness | w | 1 | m
Constant inland freshwater flux | q_f | 0.36 | m^2/day
Freshwater density | rho_f | 1000 | kg/m^3
Seawater density | rho_s | 1025 | kg/m^3
Wall locations | L_w | 0, 38, 77, 115 | m
Wall opening heights | h_w | 6, 12, 18, 24 | m

Derived:

kappa = K_w / K_a = 0.0001

Important:
- Verify the parameter table and exact meaning of H and H_s from the PDF.
- Some paper parameters (porosity, dispersivity, molecular diffusion) are for numerical transport validation and are not needed for the initial sharp-interface analytical model. Do not add them to the analytical equations unless the paper requires them.
- L_w = 0 is a wall position/configuration as defined by the paper, not automatically equivalent to removing the wall. If a no-wall baseline is needed, model it as a distinct explicit baseline case with a documented interpretation.
- The paper reports an example for h_w = 18 m with wall locations L_w = 0, 38, 77, 115 m and gives toe locations approximately 106.0, 144.0, 181.0, 188.3 m. Verify the corresponding figure/text and conditions in the PDF before using these as a strict automated test. Do not force the model to produce these values if the equations or exact configuration do not match.
- The paper gives a no-wall reference toe around 191.7 m in its results. Verify exact parameters and context before using it as a strict test.
- Treat all reference values as comparison targets with tolerances justified by rounding and source interpretation.

7. BACKEND REQUIREMENTS
Implement these endpoints (reasonable endpoint names may be adjusted consistently):

GET /api/health
- Return status, application version, and whether the scientific model module loads.

GET /api/parameters
- Return default physical parameters, units, allowed wall locations/heights, and derived alpha/kappa.

POST /api/simulate
- Accept a validated configuration (wall location, opening height, and optionally an explicit baseline mode).
- Run the analytical model.
- Return the scenario classification, toe location, profiles, units, warnings, and model metadata.
- Reject physically invalid inputs with clear HTTP 4xx errors.
- Do not return fabricated success if the equations are not implemented or the model fails.

POST /api/simulate/batch
- Run the 16 planned configurations (or an explicitly provided list).
- Return a summary and per-case errors/warnings. A single invalid case should not silently corrupt other results.

GET /api/results
- Return the latest generated case results if available, otherwise an honest empty/not-generated response.

POST /api/dataset/generate
- Run the configured batch and write generated CSV outputs.
- Return file names, number of successful cases, number of failed cases, and validation status.
- Never claim the dataset was validated merely because it was generated.

GET /api/dataset/download
- Download the generated cases/results CSV or a ZIP containing the related CSVs and manifest. If no dataset exists, return a useful error.

POST /api/validate
- Run automated checks against paper-derived reference values and mathematical/boundary-condition invariants.
- Return passed/failed checks, tolerances, and source notes.
- Validation must be distinct from simulation generation.

Optional:
GET /api/scenarios
- Return the six scenario definitions from the paper in plain language and the exact classification rules implemented.

Backend rules:
- Use Pydantic schemas for requests/responses.
- Put equations in backend/app/models/analytical_model.py, not in route handlers.
- Put classification logic in scenarios.py.
- Keep file IO in dataset_service.py.
- Add CORS configuration for the local Vite development server.
- Return clear error messages and structured error responses.
- Never silently replace invalid inputs with defaults.
- Include unit labels in API responses.
- Document all assumptions and any unsupported scenario.

4. Implement scenario classification from the paper's exact conditions.
5. Recover dimensional hydraulic-head profile and interface elevation correctly.
6. Add numerical safeguards for square roots, logarithms, divisions, and domain boundaries where they occur in the paper's equations.

1. Test alpha = 40 and kappa = 0.0001.
2. Test the parameter table and unit handling.
3. Test scenario boundary conditions and transitions.
4. Test continuity of hydraulic head at each applicable subzone boundary.
5. Test the constant inland flux boundary condition using the paper's sign convention.
6. Test the coastline boundary condition.
7. Test interface/toe conditions.
8. Test limiting/no-wall case if the paper provides a valid analytical reference.
9. Compare selected toe locations/profiles with paper results. Record the precise figure/table/equation and tolerances.
10. If a reference cannot be reproduced, investigate the model and source conditions; do not loosen tolerance just to force a pass.

Phase 4: Dataset generation
1. Generate the 16 wall configurations from the Cartesian product.
2. Record model status and scenario for every case.
3. Save case summary CSV and profile CSV.
4. Save a JSON manifest containing timestamp, model version, parameter source, assumptions, and validation status.

Phase 5: API
1. Implement endpoints and schemas.
2. Add API tests using FastAPI's test client/httpx.

Phase 6: Frontend
1. Implement dashboard and API client.
